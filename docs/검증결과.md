# 검증 결과 — 취약/양호 컨테이너 실행

- 실행 환경: Docker Desktop (Windows, Git Bash)
- 점검 대상: `docker/Dockerfile.vuln`(취약 설정 주입), `docker/Dockerfile.ok`(KISA 기준 충족 설정)
- 실행 명령:
  ```bash
  docker build -f docker/Dockerfile.vuln -t checker:vuln .
  docker run --rm checker:vuln > results/vuln.json

  docker build -f docker/Dockerfile.ok -t checker:ok .
  docker run --rm checker:ok > results/ok.json
  ```
- 결과 파일: `results/vuln.json`, `results/ok.json`
- 최종 검증 결과: **취약 컨테이너 25/25, 양호 컨테이너 25/25 — 전 항목 기대값과 일치, 오탐·미탐 0건**
- 비고(U-26, U-28 취약 재현): 패치관리 영역은 Docker 빌드 시점마다 실제 패키지 버전 차이를 고정하기 어려워, `docker/Dockerfile.vuln`에서 `apt`/`ssh`/`openssl` 명령의 출력을 모의하는 래퍼 스크립트로 "미적용 업데이트 존재", "구버전 OpenSSH·OpenSSL" 상태를 재현함(판정 로직 자체는 실제 명령 출력 형식을 그대로 파싱)
- 비고(U-29 디버깅): 첫 실행에서 취약 컨테이너의 U-29가 "양호"로 미탐 — `U-29.sh`의 journald Storage=auto 폴백 로직 자체는 정상이지만(`/var/log/journal`이 존재하면 실제로 영구 저장이 동작하는 게 맞음), `ubuntu:22.04` 베이스 이미지에 이 디렉터리가 기본 생성되어 있어 rsyslog 미설정만으로는 취약 상태가 재현되지 않았음. `docker/Dockerfile.vuln`에 `RUN rm -rf /var/log/journal`을 추가해 영구 저장 디렉터리를 명시적으로 제거하도록 수정 후 재검증, 취약으로 정상화됨. (점검 스크립트 버그가 아니라 취약 컨테이너 설계의 허점이었음)

## 3. Windows 서버 — 실제 환경 실행 결과 (15개 전 항목 — 계정관리 5 + 서비스관리 4 + 패치관리 1 + 로그관리 2 + 보안관리 3)

- 실행 환경: 실제 Windows 10/11 PC(관리자 권한 PowerShell), **Docker 컨테이너 기반 양호/취약 양쪽 교차검증이 아님**
  — Linux 점검은 Dockerfile.ok/Dockerfile.vuln 두 가지 고정된 상태를 만들어 기대값과 실제값을 전부 대조했지만,
  Windows는 아직 "의도적으로 취약하게 설정한 기준 환경"을 따로 준비하지 않고 평소 쓰는 실제 PC에 그대로 실행함.

  확인하는 스모크 테스트**이며, Linux처럼 양호/취약 양쪽 기대값과 대조하는 완전한 검증은 아님.


- 비고(secedit 인코딩 버그): 1차 실행 이후 `lib/common.ps1`의 `Get-SecPolicyValue`에서 `secedit /export` 결과 파일이
  UTF-16(유니코드)로 생성되는데 `Select-String`이 이를 지정하지 않아 패턴 매칭이 전부 실패하던 문제를 발견해

  항목이 N/A로 나왔어야 하는데, 실제로는 값이 정상적으로 읽혀 처음부터 문제가 없었거나 이미 수정된 상태로 검증됨.
- 비고(W-34 파일 손상): `checks/windows/W-34.ps1`이 한 차례 알 수 없는 원인(컴퓨터 간 외장하드 동기화 또는 편집기

  재검증 결과 정상 동작 확인.
- 비고(Get-NetTCPConnection 미사용): W-21/W-34 둘 다 `Get-NetTCPConnection` 호출이 예외로 빠져 `netstat` 폴백 경로로
  판정됨(이 PC에서 NetTCPIP 모듈 관련 제약으로 추정) — 판정 자체는 정상 동작했으므로 문제는 아니나, 추후 원인을
  확인해 `Get-NetTCPConnection`이 정상 동작하는 환경에서도 결과가 같은지 추가 확인 예정.
- 비고(PowerShell 실행 정책 / `-AsArray` 환경 이슈): 다른 컴퓨터에서 처음 실행했을 때 Windows 기본 실행 정책
  (Restricted)에 막혀 `run_all_windows.ps1` 자체가 로드되지 않음 — `Set-ExecutionPolicy -Scope CurrentUser
  -ExecutionPolicy RemoteSigned -Force`로 해결. 또한 `ConvertTo-Json -AsArray`는 PowerShell 6.0+ 전용 매개변수인데
  Windows 기본 PowerShell은 5.1이라 매개변수 오류가 났음 — 결과가 1건일 때만 배열로 안 감싸지는 문제를 수동으로
  보정하도록 `run_all_windows.ps1`을 수정함.
- 비고(인코딩/mojibake 버그 — 가장 핵심적인 원인): 뒤에 추가한 `.ps1` 스크립트들을 두 번째 컴퓨터에서 직접 실행하니
  한글이 깨져서(`?덉??ㅽ듃由?` 등) 파싱 에러(`UnexpectedToken`)가 났음. 원인은 해당 `.ps1` 파일들이 BOM(Byte Order
  Mark) 없는 UTF-8로 저장돼 있었고, Windows PowerShell 5.1이 BOM이 없으면 시스템 기본 코드페이지(한글 Windows는
  CP949)로 파일을 읽어버리는 것 — 파일 내용 자체는 처음부터 정상이었고, PC마다 다른 읽기 방식 때문에 생긴 문제였음.
  원본 바이트를 UTF-8로 명시적으로 다시 읽어 BOM 포함 UTF-8로 재저장해 해결했고, 이후 작성한 W-39·W-40·W-42는
  처음부터 BOM 포함 UTF-8로 저장해 재발을 방지함.
- 비고(W-39/W-40/W-42 추가 검증): W-39(백신 정의 최신성)는 Windows Defender 정의가 130시간 넘게 갱신되지 않아
  취약으로 정상 판정됨. W-40(감사 정책)·W-42(이벤트 로그 설정)은 이 PC에서 둘 다 양호로 판정됨 — 12개 항목 통합
  실행이 오류 없이 완료된 것을 확인함.
- 비고(W-40/47/52 BOM 재발): 15개 전체를 처음 돌렸을 때 W-40, W-47, W-52가 "표준출력이 올바른 JSON이 아님"으로 N/A 처리됨.
  세 파일 모두 BOM이 빠진 상태로 저장돼 있었던 것이 원인(BOM이 빠진 경위는 미확인) — BOM을 다시 넣은 뒤 재실행해
  15/15 정상 실행 확인. 새 `.ps1`을 추가하거나 옮긴 뒤에는 파일 첫 3바이트(EF BB BF)를 확인할 것.
- 비고(2차 검증 필요): 이 PC가 "원래부터 취약하게 설정돼 있었는지"와 "스크립트가 맞게 판정했는지"는 구분이 안
  되므로, 양호/취약이 나온 항목들의 설정을 교차로 바꿔가며(예: `net accounts /lockoutthreshold:5`로 바꾼 뒤
  재실행해 W-04가 양호로 바뀌는지 확인) 재실행하는 2차 검증이 필요함 — 15개 항목 구현이 끝났으므로 다음 단계로 진행 예정.
